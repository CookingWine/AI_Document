# AIRule 说明（给 AI 立规矩）

> **这套文档写给谁**
> 没怎么用过 AI，也没写过代码的人。
>
> **你需要会什么**
> 会开文件夹、会打字、会复制粘贴，就够了。其他都在这里讲。
>
> **读完你能做到什么**
> 用一页纸，把你"绝对不能容忍"和"一定要这样"的事写清楚，让 AI 每次都守住，不用你每次盯着。

---

## 先读这个：用三句话认识 AIRule

**第一句**：AI 干活时，最让人头疼的不是它不会做，而是它**做过了头**——自作主张改了你没让它改的文件、编了个看起来很真的数字、顺手把你原来的格式全打乱了。

**第二句**：这些事有个共同点：**它每次都犯，你每次都得再说一遍**。因为它不记得上次你骂过它什么。

**第三句**：AIRule 就是**把"不许做的事"和"必须这样做的事"提前写在一张纸上，放在它每次开工都能看见的地方**。写完一次，往后每一次都生效。

一句话记住区别：

| 你想要的 | 该用什么 | 在本仓库哪一套 |
| --- | --- | --- |
| 让它**把一件事干完** | AIAgent | [AIAgents](../AIAgents/README.md) |
| 让它**遇到这类活按固定做法干** | AISkill | [AISkill](../AISkill/README.md) |
| 让它**任何时候都别越界** | **AIRule** | 你在这里 |

| 怎么把活派给 AI、怎么验收 | [AIAgents 说明](../AIAgents/README.md) |

**一句话区分三套文档**：`AIRule` 管**边界**（不能做什么），`AISkill` 管**做法**（这类活怎么做），`AIAgents` 管**执行**（把活派出去、盯完成）。

打个比方，这三样对应一家餐厅里的三样东西：

- **AIRule** = 贴在墙上的**卫生守则**。不管谁进厨房，都得遵守，不用谁来喊。
- **AISkill** = 一本**菜谱**。要做宫保鸡丁了，才翻开那一页。
- **AIAgent** = **厨师本人**。菜谱再厚、守则再严，也得有人动手炒。

守则不需要被"想起来"，它一直在墙上。这就是 AIRule 跟另外两样最根本的不同。

## 三条阅读路径

不用按顺序读完。看你是哪种情况。

**路径一：完全新手，想系统搞懂（约 35 分钟）**

```
01 什么是规则 → 02 认识 AIRule → 03 什么该写成规则
   → 04 怎么写 → 05 层级与优先级 → 06 怎么用起来
```

**路径二：不想听道理，今天就要用上（约 12 分钟）**

```
02 认识 AIRule（只看 2.2 的例子）
   → 04 怎么写（照着 4.4 的骨架填）
   → 06 怎么用起来（放好，跑一次验证）
```

遇到不懂的词，随手翻 [09 术语表](./docs/09-术语表.md)。

**路径三：已经出问题了**

```
先看 07 常见错误 → 再看 04 的 4.3 好坏对照
   → 还不行就看 08 常见问题
```

## 文件之间的关系

```
README（入口：索引 + 三条阅读路径）
   │
   ├─▶ 01 什么是规则
   │      └─▶ 02 认识 AIRule
   │             └─▶ 03 什么该写成规则
   │                    └─▶ 04 怎么写一条规则
   │                           ├─▶ 05 层级与优先级
   │                           ├─▶ 06 怎么用起来
   │                           └─▶ 07 常见错误
   │                                  └─▶ 08 常见问题
   │
   ├─▶ 09 术语表（随时可查，不参与顺序阅读）
   │
   └─▶ templates/（被 04、06、07 引用）
          ├── RULE-模板
          └── 规则清单-模板
```

四条规则，记住就不会乱：

1. **`README.md` 是唯一入口。** 不要让同事"从中间某篇开始摸索"，入口永远先给这篇。
2. **01 → 04 是学习顺序。** 倒着读会缺前提，比如没看 03 的边界判断，04 写出来的规则会又长又没用。
3. **`04` 依赖 `templates/`。** 第 4 步要照着模板填空，模板改了，04 里的说明要同步。
4. **`05`、`06` 是并列的两件事。** 一个管"多条规则怎么不打架"，一个管"规则怎么落地生效"，先看哪个都行，但两个都得看。

每篇文件的开头都标了"读这篇之前"，结尾都标了"下一篇"，跟着走不会迷路。

## 维护约定

**改哪一篇**

| 你想改的内容 | 改哪个文件 |
| --- | --- |
| 新增一个概念的讲解 | `docs/01-什么是规则.md` |
| 调整"什么该写成规则"的判断标准 | `docs/03-什么该写成规则.md` |
| 补充一条措辞技巧或好坏例子 | `docs/04-怎么写一条规则.md` |
| 补充一条新手易错点 | `docs/07-常见错误.md` |
| 回答了一个新问题 | `docs/08-常见问题.md` |
| 新增术语 | `docs/09-术语表.md`，并在首次出现的正文里加链接 |
| 模板填空项变了 | `templates/` 下对应文件，并同步 `04`、`06` 的说明 |

**四条硬规则**

1. **一篇只讲一件事。** 想加的内容放不进现有任何一篇，才新建文件，并更新本页索引和结构图。
2. **这套文档只管规则层。** 一类活怎么干、怎么派活，一律链接到 `AISkill/`、`AIAgents/`，不在这里复述，避免同一件事两处维护、两处走样。
3. **引用一律用相对路径。** 写 `../AISkill/README.md`，不写 `/Users/你/...`。
4. **变更以提交记录为准。** 目录内不单独维护变更日志，`git log -- AIRule/` 就是这套文档的历史。

**新增一篇的步骤**

1. 在 `docs/` 下按序号命名，比如 `10-团队协作规则.md`。
2. 复制任意一篇的文件头（所属、读前、读完、相关文件），改成自己的。
3. 在本页"文件索引"表里加一行。
4. 上一篇文章的结尾导航加一个"下一篇"。
5. 更新本页结构图。

## 最后一句话

不要一上来就写二十条。**先写三条你最受不了的**，跑一周，看看它是不是真的守住了。守住三条，比写下二十条没人看强得多。
