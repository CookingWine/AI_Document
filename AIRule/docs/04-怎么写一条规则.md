前三篇讲的是"为什么要写、该写什么"。这一篇开始动手。

先说一句让人安心的话：**写规则不需要文笔。** 它更接近写"注意事项"，而不是写文章。写得漂亮但没法执行，不如写得笨但一眼能懂。

---

## 4.1 好规则的四个特征

拿这四条去量你写的每一条，缺哪条补哪条。

| 特征 | 什么意思 | 反例 | 正例 |
| --- | --- | --- | --- |
| **可判断** | 违反没违反，一眼能看出来 | 写得专业一点 | 不用"亲""哈"这类语气词 |
| **可执行** | 看完就知道该做什么动作 | 注意数据准确性 | 数字必须标出处，没有就写【待确认】 |
| **够短** | 一条只说一件事 | 一段话里塞了五个要求 | 拆成五条，一条一行 |
| **有边界** | 说清了管哪些活 | 回复要简洁 | 所有对外发出的邮件要简洁，内部记录不限 |

四个里最常缺的是**可判断**。原因很简单：我们平时说话习惯用形容词（专业、简洁、自然、高级），而形容词在 AI 那里会自动翻译成它自己的理解。

**一个立刻能用的转换法**：把形容词换成**看得见的东西**。

| 你说 | 换成 |
| --- | --- |
| 简洁一点 | 每段不超过 4 行 |
| 专业一点 | 不用语气词，不用感叹号，不用"我觉得" |
| 自然一点 | 不用"首先/其次/最后"这类连接词开头 |
| 高级一点 | 不用 emoji，不用"超级""非常"这类程度词 |
| 别太啰嗦 | 结论放第一句，背景不超过两句 |

## 4.2 用否定句，别用祈使句

这是本篇最反直觉、也最有效的一条。

新手写规则，习惯写"要怎么做"：

```
- 要仔细核对数据。
- 要保留原文的风格。
- 要考虑读者的感受。
```

这些话听起来都对，但 AI 照做的时候，它得先自己判断"什么叫仔细""什么叫原文风格"。判断的过程就是自由发挥的过程——**发挥的空间，就是出错的空間。**

换成否定句：

```
- 不许出现任何未经核对的数字。没核对过就标【待确认】。
- 不许改动原文的句子顺序和标点。
- 不许在回复里评价我的想法。
```

否定句的好处是**把判断权收回你手里**：它不需要理解"仔细"是什么，只需要检查"有没有出现没核对的数字"。

> 💡 **为什么"不要"比"要"管用**
> 因为"要"描述的是一种状态（好的、专业的、简洁的），而"不要"描述的是一件具体的事（出现感叹号、加了总结段、改了标题）。
> **状态没法验收，具体的事可以。**

但也不是全用否定句。**统一口径类的要求，只能用肯定句**：

```
- 产品名统一写"轻记"。
- 日期一律写 2026-10-28 这种格式。
```

所以正确的配比是：**红线用否定句，口径用肯定句。**

## 4.3 十组好坏对照

这一节可以当字典查。左边是你现在大概会写的，右边是改完之后。

| # | ❌ 不好 | ✅ 好 | 问题在哪 |
| --- | --- | --- | --- |
| 1 | 回答要专业 | 回复里不出现"我觉得""可能吧""应该是"，不确定就直说"我不确定" | "专业"没法判断 |
| 2 | 不要编造内容 | 数字、日期、人名、引语必须有出处；没有出处就写【待确认】 | 少了可执行的替代动作 |
| 3 | 改的时候小心点 | 只改我标出来的段落。发现别处有问题，列清单告诉我，不要顺手改 | "小心"不是动作 |
| 4 | 格式要统一 | 标题用"一、二、三"，不用"1. 2. 3."；正文不用加粗 | 没说统一成什么样 |
| 5 | 尽量简短 | 每段不超过 4 行；结论放第一句；不写总结段 | 形容词换成数字 |
| 6 | 别太机械 | 不用"首先/其次/最后"开头；不用"综上所述" | 把感觉翻译成特征 |
| 7 | 注意保密 | 不在回复里复述客户的手机号、身份证号、住址；需要引用时只写后四位 | 没说具体哪些字段 |
| 8 | 有问题问我 | 遇到以下三种情况必须先问我：要删文件、要外发内容、要花钱 | 没说"哪些情况" |
| 9 | 中文回答 | 用中文回复；技术名词保留英文原词，不硬译 | 补上例外，防止乱翻 |
| 10 | 别乱改我的稿子 | 不许改标题、不许调段落顺序、不许替换我的用词（错别字除外） | 一条拆成三个具体禁止 |

看完这十组，规律很清楚：**每一条修改，都是把"形容词"换成"能数、能查、能列举的东西"。**

## 4.4 一条规则的骨架

单条规则照这个填，四行就够：

```
- 【什么时候】在做 ____ 的时候，
  【不许/必须】____，
  【怎么算做到了】____，
  【例外】除非 ____。
```

实际的例子：

```
- 在整理我提供的资料时，不许补充资料里没有的事实；
  判断标准是：每个事实性句子都能在原文里找到对应的一句；
  除非我明确说"可以补充背景"，那也只补公开可查的通识，并标明"补充"。
```

日常写的时候不用真把这四个标签写出来，写顺了自然就带上了：

```
- 整理资料时只用手上有的内容，每个事实句都要能在原文找到对应；
  我明确说"可以补充背景"时例外，那时只补公开通识并标注"补充"。
```

## 4.5 整份文件的骨架

单条规则会写了，再看整份文件怎么排。

**三段式**，几乎适用于所有场景：

```markdown
# ____ 规则

## 一、绝不做的事
（红线。违反一次就不能接受的，放这里。3–5 条。）

## 二、必须这样
（统一口径。格式、语气、命名、数字写法。3–8 条。）

## 三、拿不准的时候
（出口。遇到什么情况停下来问，而不是自己决定。）
```

**为什么是这个顺序**：最要紧的放最前面。AI 读长文件时，开头和结尾的注意力最强，中间最容易被忽略。红线必须在开头。

**第三节为什么不能省**：没有出口的规则，遇到特殊情况只有两个下场——要么 AI 硬着头皮违规，要么它自作主张绕过去，两种你都不想要。给它一个"停下来问"的许可，比让它猜要好。

第三节的写法有个小技巧：**列举，不要概括。**

```
❌ 遇到不确定的情况先问我。          ← "不确定"太宽，它不会问
✅ 遇到这三种情况必须先问：
   1. 要删或覆盖任何已有文件
   2. 要把内容发给公司以外的人
   3. 涉及金额、承诺、时间节点的表述
```

## 4.6 长度与分组

**一条规则只说一件事。** 一句话里出现两个"并且"，就该拆。

看这个反例：

```
- 回复要简洁并且不要用术语并且结论放前面并且不要加总结。
```

拆成四条，不是为了好看，是因为**拆开之后你能单独验收**：哪条被违反了，一眼看得出来。挤在一起，你只知道"这次不太对"，说不清哪儿不对。

**分组用二级标题，不要超过三组。** 分太多组，找起来比不分组还慢。

推荐的三种分法，选一种就行：

| 分法 | 适合 | 分组名示例 |
| --- | --- | --- |
| 按强度分 | 大多数情况，推荐 | 绝不做的事 / 必须这样 / 拿不准怎么办 |
| 按对象分 | 涉及多种产出 | 写文字时 / 做表格时 / 改文件时 |
| 按后果分 | 风险高的场景 | 不能碰的 / 要确认的 / 自由的 |

## 4.7 写完立刻做一次自检

不用等别人看，自己过这五关：

1. **每条都能判断违反了吗？** 随便挑三条，想象一下"它违反了"长什么样。想不出来，就是写虚了。
2. **有没有形容词？** 搜一遍"专业、简洁、自然、合适、尽量、适当"。有就换掉。
3. **有没有一条塞了三件事？** 有就拆。
4. **第三节写了吗？** 没写"拿不准怎么办"，规则就是一张没有出口的网。
5. **念一遍，像不像人话？** 规则是给人看的，也包括三个月后的你。写得太像法条，你自己都不想改它。

> 💡 **一个快速的土办法**
> 把规则文件发给 AI，然后随便派一件不相干的活，看它会不会主动提一句"按规则我不做 X"。
> 会提，说明规则被读进去了；完全不提，可能是放错位置了——见 [06 怎么用起来](./06-怎么用起来.md)。

---

## 本篇要点

- 好规则四特征：可判断、可执行、够短、有边界。
- 把形容词换成看得见的东西——这是最见效的一招。
- 红线用否定句，口径用肯定句。
- 整份文件三段式：绝不做的事 / 必须这样 / 拿不准怎么办。
- 一条只说一件事，拆开才能单独验收。
