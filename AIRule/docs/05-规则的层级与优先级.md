# 05 规则的层级与优先级

写一条规则不难。写二十条、又分属不同项目的时候，问题才真正开始：**它们会打架。**

这一篇解决两个问题：规则该放哪一层；打架了听谁的。

---

## 5.1 为什么必须分层

假设你把所有规则都塞进一个文件：公司的保密要求、你这个项目的排版要求、还有"这次先别改代码注释"这种临时要求。

会发生三件事：

| 后果 | 具体表现 |
| --- | --- |
| 每次开工都要读一遍无关内容 | 做 A 项目的事，还得读 B 项目的排版规矩 |
| 临时要求永远删不掉 | "这次先别改注释"，三个月后还躺在里面 |
| 打架时不知道该删哪条 | 两条都写着，一条说简洁，一条说要详列 |

分层就是解决这三件事的：**不同寿命、不同适用范围的东西，放不同地方。**

---

## 5.2 三层结构

| 层级 | 放什么 | 放哪儿 | 生效范围 | 寿命 |
| --- | --- | --- | --- | --- |
| **全局层** | 跟你这个人、这个团队永远相关的底线 | 用户级配置目录，或工具的"全局规则"设置 | 你所有的活 | 年级 |
| **项目层** | 只跟这个项目有关的红线与口径 | 项目根目录的规则文件 | 这一个项目 | 月级 |
| **单次层** | 只对这次任务有效的要求 | 当次对话里说 | 这一次 | 小时级 |

三层的区别，用一句话概括：**越往下越具体，越往上越硬。**

还是餐厅的比方：

- **全局层** = 食品安全法。开几家店都得守。
- **项目层** = 这家店的厨房动线、菜品标准。只在这家店有效。
- **单次层** = "今天有位客人不能吃辣，他那份别放辣椒"。今天过了就作废。

> 💡 **放错层的典型症状**
> - 把项目专用要求写进全局 → 做别的项目时天天被误伤
> - 把通用底线只写在项目里 → 换个项目，同样的错再犯一次
> - 把临时要求写进持久文件 → 文件越养越肥，最后没人看

---

## 5.3 打架了听谁的

两条规则冲突时，按这两条判，顺序不能颠倒。

**第一条：就近原则。** 越靠近具体任务的规则，优先。

理由很实在：写在项目里的规则，是知道这个项目具体情况的人写的；写在全局的规则，是为了通用而写的。**具体的压过通用的。**

```
全局：回复要简洁，每段不超过 4 行
项目：法律意见书必须完整引用条文原文，不受长度限制
      ↓
本项目里，以项目规则为准
```

**第二条：硬规则优先于软规则。** 红线类的（不许删文件、不许外发）永远压过风格类的（简洁、统一格式）。

```
项目：报告尽量写得紧凑
全局：任何数字必须标出处
      ↓
冲突时，出处优先。"紧凑"可以让步，"出处"不能让
```

两条一起用，判断顺序是：

```
1. 是不是红线？        → 是红线的那条赢
2. 都不是红线？        → 范围更近的那条赢
3. 范围也一样近？      → 后写的赢（新规则覆盖旧规则），并把旧的删掉
```

第三步要特别注意：**"后写的赢"是应急手段，不是常规做法。** 如果经常靠"后面覆盖前面"来解决，说明你在该删的地方选择了叠加，文件迟早会烂掉。

---

## 5.4 画成图就是这样

```
全局层（你的底线）
  不许删文件 · 数字要出处
        │
        │ 被继承
        ▼
项目层（本项目的口径）
  产品名写"轻记" · 表格格式
        │
        │ 被继承
        ▼
单次层（这次的要求）
  这次先只改第二节

冲突时的裁决：
① 红线 > 风格
② 近 > 远
③ 同层同性质 → 新的覆盖旧的（并删掉旧的）
```

**继承的意思是**：下层不用重复写上层的内容。全局写了"数字要出处"，项目里就不用再写一遍。重复写不但浪费篇幅，还会在将来改的时候漏改一处，变成两个版本。

---

## 5.5 例外怎么写

规则一定会遇到"这次不适用"的情况。写法有两种，效果差很远。

**❌ 在规则末尾加一句"特殊情况除外"**

```
- 回复不超过 4 行。特殊情况除外。
```

"特殊情况"是什么情况？AI 不知道，你事后也说不清。这句话等于给规则开了个后门，任何它不想遵守的时候都能钻。

**✅ 把例外写死，并指明谁来定**

```
- 回复不超过 4 行。
  例外：用户明确要求"详细展开""给我完整方案"时不受此限。
  其他情况需要放宽，先问我。
```

三个要点：

1. **例外条件要具体**——"用户明确要求详细展开"，这是能识别的信号。
2. **要说清谁来决定**——"先问我"，而不是"自行判断"。
3. **例外只开一个口子**——不要列五个例外，那说明这条规则本身没想清楚，该重写。

> ⚠️ **"自行判断"是个陷阱**
> 凡是写"视情况而定""酌情处理""灵活把握"的地方，等于把决定权交给了 AI 的猜测。
> 你真正想要的通常是：**"拿不准就停下来问我"**。把这句写进去，比写"酌情"有用一百倍。

---

## 5.6 什么时候该拆层

不用一上来就分三层。出现下面任一信号，再动手拆。

| 信号 | 该怎么拆 |
| --- | --- |
| 规则超过 15 条 | 把通用的提到全局，项目专属的留下 |
| 做不同项目时要反复提醒"这次不用管那条" | 那条本来就该在项目层 |
| 同一条规则在两个项目里要求不一样 | 说明它其实不是全局规则，下沉到项目 |
| 每次都要临时加一句"这次先别…" | 这类要求本来就不该写进文件 |

拆的动作很小：**把文件里的一段剪走，贴到另一层去，原位置留一行指向说明。**

```
（项目规则文件里）
本项目的通用底线见全局规则；以下是本项目补充的三条：
```

---

## 本篇要点

- 三层：全局（年级）、项目（月级）、单次（小时级）。越往下越具体。
- 冲突裁决三步：红线优先 → 近的优先 → 同层则新的覆盖旧的。
- 下层继承上层，不要重复写。重复写迟早改漏一处。
- 例外要写死条件、指明谁定，不要写"特殊情况除外"。
- 出现"每次都要临时说明"的情况，说明分层错了。
