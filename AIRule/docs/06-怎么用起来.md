# 06 怎么用起来

> **所属**：AIRule 说明 › 第六部分 落地
> **读这篇之前**：[04 怎么写一条规则](./04-怎么写一条规则.md)
> **读完你能**：把写好的规则放到正确位置，确认它真的生效了，并知道什么时候该改它
> **相关文件**：[层级与优先级](./05-规则的层级与优先级.md) ｜ [RULE-模板](../templates/RULE-模板.md) ｜ [上一篇](./05-规则的层级与优先级.md) ｜ [下一篇](./07-常见错误.md)

---

规则写完了，如果放在一个 AI 根本不会去读的地方，那它只是一篇作文。

这一篇讲三件事：**放哪儿、怎么确认生效、怎么养。**

---

## 6.1 放在哪儿

原则只有一句：**放在 AI 每次开工都会自动读取的位置。**

这个位置不是统一的，各家工具约定不一样。常见的几种：

| 工具 / 场景 | 常见位置 | 生效范围 |
| --- | --- | --- |
| Claude Code | 项目根目录 `CLAUDE.md`；全局在用户配置目录下 | 项目 / 全局 |
| Cursor | 项目内 `.cursor/rules/` 下的规则文件 | 项目 |
| GitHub Copilot | 项目内 `.github/copilot-instructions.md` | 项目 |
| 通用约定（多数 agent 工具支持） | 项目根目录 `AGENTS.md` | 项目 |
| 支持自定义的 agent 平台 | 工具设置里的"全局规则""自定义指令"输入框 | 全局 |

> ⚠️ **别照抄，去查一下**
> 上面这张表是常见约定，各工具改版频繁，文件名和目录可能变。
> **以你正在用的那个工具的官方说明为准。** 查法很简单：在它的设置里找"Rules""Instructions""记忆""自定义指令"这类词，或者搜"你的工具名 + rules 放在哪"。
>
> 找不到也别慌：几乎所有工具都提供了"全局自定义指令"的输入框，把规则贴进去同样有效。

**一个实用的判断方法**：把规则文件放好之后，新开一个对话，直接问它：

```
你现在能看到的规则有哪些？请复述一遍。
```

它念得出来，位置就对了；念不出来，就是没被读到。

---

## 6.2 三层分别放哪儿

对应 [05 层级](./05-规则的层级与优先级.md) 的三层，落地位置是这样：

```
你这个人（全局）
   └─ 工具设置里的"全局规则"，或用户配置目录下的规则文件
        │
        │ 继承
        ▼
这个项目
   └─ 项目根目录：AGENTS.md / CLAUDE.md / .cursor/rules/ …
        │
        │ 继承
        ▼
这次任务
   └─ 当次对话里直接说
```

**新手只需要做两件事**：项目根目录放一份（管这个项目），工具设置里放一份短的（管所有项目）。

短的那份写什么？三到五条最硬的就行，比如"中文回答""不许编数字""不许删文件不问"。别把项目的排版要求塞进去。

---

## 6.3 怎么确认它真的生效了

写完不算完，得验。三个方法，从轻到重。

### 方法一：让它复述

新开一个对话，问：

```
你现在遵守哪些规则？按条目列出来。
```

- **能列出来，且和原文一致** → 读到了。
- **列得含糊，或漏了几条** → 可能读到了但没重点。检查是不是写太长、红线是不是被埋在中间。
- **完全不知道你在说什么** → 位置错了，或文件名不对。

这个方法验的是"有没有读到"，不验"会不会遵守"。

### 方法二：故意试探

挑一条你最在意的红线，派一个会踩线的活。

比如规则里有"不许编数字"，就问：

```
帮我写一段介绍，说一下我们产品去年的增长率。
（不要提供任何数据）
```

**期待的反应**：它问你"增长率是多少"或者标【待确认】。
**不该出现的反应**：它直接写一个"增长了 37%"。

这个方法最有效，因为它验的是真实行为。**建议每条红线都试一次**，尤其"不许删文件""不许外发"这两类——这两类出事代价最大。

### 方法三：对比

同一件事，加规则前后各做一次，对比结果。

这个方法慢，但最直观。适合你在犹豫"这条规则到底有没有用"的时候。

> 💡 **一个容易忽略的细节**
> 有些工具只在**新开的对话**里加载规则，当前对话不会立刻生效。
> 改完规则文件，记得开一个新对话再测。

---

## 6.4 怎么养：四个该动的信号

规则不是写完就锁死的。出现下面四种情况，就该动手改。

| 信号 | 说明 | 怎么改 |
| --- | --- | --- |
| **同一条错犯了三次** | 规则里没有这一条，或者写了但太模糊 | 补一条，或把模糊的那条改具体 |
| **同一条规则三个月没触发过** | 要么你不再做这类活，要么它本来就是多余的 | 删掉。留着只会稀释重点 |
| **你每次都要口头补一句** | 这句话本该在文件里 | 补进去，或检查是不是放错了层 |
| **两条规则开始打架** | 通常是把不同层的东西塞在了一起 | 按 [05](./05-规则的层级与优先级.md) 拆层 |

**修改的动作要小。** 一次只改一两条，改完跑一次验证。一次改十条，出了问题你分不清是哪条的锅。

---

## 6.5 版本与记录

规则文件也是个文件，会被人改、会被忘。留痕很便宜，收益很高。

最小做法，在文件末尾加五行：

```markdown
## 生效与修改
- 建立：2026-10-20，起因是三次编造数据
- 2026-10-25：新增"不改标题"，被改过两次
- 2026-11-02：删除"不用表格"，已不再做表格类任务
- 维护人：李
```

**为什么值得写**：半年后你想删某一条，看到"起因是三次编造数据"，就知道不能删。没有这行记录，你只会觉得"这条好像没什么用"。

如果你用 Git 管这个文件夹（像本仓库一样），那更省事：`git log` 就是记录。但**"为什么定这条"这种信息，提交信息里常常没写清楚**，所以文件内留一句仍然值得。

## 6.6 给同事用

规则文件最大的价值之一是**可复制**。同一份文件发给五个人，五个人的 AI 都按同一套标准干活。

三个注意点：

1. **先删掉只跟你有关的内容。** 你的路径、你的偏好、你的项目代号，别人用不上，还会造成误伤。
2. **写清"这份规则假设了什么"。** 比如"本规则假设你在做中文内容"，别人做英文内容时就知道要改。
3. **别只发文件，附一句怎么用。** 放在哪个目录、要不要新建对话。一句话能省对方半小时。

---

## 6.7 第一周怎么走

如果你现在什么都没有，按这个顺序走，一周就能跑顺。

| 时间 | 做什么 |
| --- | --- |
| 第 1 天 | 写下你最受不了的 **3 条**，放进项目根目录。不要多写 |
| 第 2 天 | 用 6.3 的方法二，逐条试探，看是不是真的守住了 |
| 第 3–5 天 | 正常干活。每次你忍不住口头补一句，就把那句记在便签上 |
| 第 6 天 | 把便签上的话收进规则文件，同时删掉从没触发过的条目 |
| 第 7 天 | 把最硬的两三条提到全局层，让别的项目也受益 |

一周之后你手上会有一份五到八条、每条都真的被验证过的规则。**这比一开始写三十条有用得多。**

---

## 本篇要点

- 放在 AI 每次开工都会自动读的位置；具体位置查你所用工具的说明，别照抄。
- 三个验证法：让它复述、故意试探、前后对比。红线条条都该试一次。
- 改完规则要开新对话才生效。
- 四个该动的信号：犯三次、三月没触发、总要口头补、两条打架。
- 一次只改一两条，改完就验。
