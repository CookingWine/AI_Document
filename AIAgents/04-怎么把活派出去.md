## 4.1 起步三条原则

1. **小步**：第一次派活，控制在"十分钟能验完"的规模。别拿整个项目试水。
2. **可验收**：派活的同时想好"什么样算完成"，最好能逐条打勾。
3. **可回滚**：动手前先有备份或版本管理，最差也能 `git checkout` 回来。

---

## 4.2 派活五段式

大多数人派活失败，不是 AI 不行，是**只说了目标，没说边界和终点**。按这五段写，成功率高得多：

```
目标：把【什么】变成【什么】，交付到【哪里】
输入：这几份是准的（列出路径）；那几份是旧的，不要用
约束：不要改【哪些】；输出用【什么格式】；最多花【多少时间/成本】
验收：满足这【几条】算完成（可逐条打勾）
停止：遇到【什么情况】停下来问我，不要自己决定
```

五段各管什么：

| 段落 | 不管会怎样 |
| --- | --- |
| 目标 | 它不知道要做到哪一步算完，容易半途交差 |
| 输入 | 它读了不该读的旧资料，越认真错得越远 |
| 约束 | 它顺手改了你不想动的东西，或者输出格式要返工 |
| 验收 | 你只能凭感觉说"不太对"，改也不知道改哪里 |
| 停止 | 它卡住了也不喊人，编一个答案交给你（见 [02 篇的两种失败](./02-任务是怎么跑完的.md)） |

对照一下差别：

| 说法 | 结果 |
| --- | --- |
| "帮我把会议记录整理一下" | 它按自己的理解整理，格式、详略全靠猜 |
| "把 `meetings/` 下 10 月的 3 份记录合并成一份复盘，输出到 `review/10月复盘.md`；只保留决议和待办，删掉寒暄；每项待办要标负责人；如果某份记录缺少负责人，先在文末列出缺项，不要自己编；改完把文件列表报给我" | 结构、范围、异常处理都定了，产出基本可预期 |

差别不在字数，在于**后一句里有验收标准和停止条件**。

## 4.3 任务怎么拆

拆到"一步一验"就够了，不用拆到原子级。

| 拆得太粗 | 拆得合适 | 拆得太细 |
| --- | --- | --- |
| "整理公司资料" | "把 `docs/` 下的文档按主题分成四类，输出分类表" | "打开第一个文件，读第一段，判断主题……" |
| 它无从下手 | 每步有明确产出，错了能马上发现 | 你在替它写程序，不如自己干 |

一个实用信号：**如果一步做完，你没法在三十秒内判断对不对，就再拆一层。**

---

## 4.4 权限与安全边界

| 做法 | 具体怎么设 |
| --- | --- |
| 只读优先 | 第一轮只让它读和报，确认理解对了再放开写 |
| 危险操作二次确认 | 明确要求：删除、覆盖、对外发送前必须先问你 |
| 先备份 | 动手前复制一份，或确认目录在版本管理下 |
| 最小权限 | 用专门的、权限受限的账号，别给它主账号密钥 |
| 敏感数据 | 客户名单、身份证号、合同金额不进对话；需要时先脱敏 |
| 小批量 | 批量操作分批做，每批不超过十来个文件，做完抽查 |

---

## 本篇要点

- 派活失败多半不是 AI 不行，是**只给了目标，没给边界和终点**。
- 五段缺一不可：**目标、输入、约束、验收、停止**；其中"停止"最容易被忘，也最致命。
- 拆到"一步一验"即可，判断信号是**三十秒内能不能看出对错**。
- 权限从**只读**起步，危险操作留一道人工确认。
