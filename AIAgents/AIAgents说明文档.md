## 一、简介：AIAgent 是什么

### 1.1 一句话定义

**AIAgent 是一个能自己动手、把一件事从头做到尾的 AI，不只是陪你一问一答。**

**打个比方**：聊天机器人像**电话客服**——你问一句它答一句，挂了电话就不再管你的事；AIAgent 像**派出去办事的同事**——你说"把上个月的会议记录整理成一份复盘"，他自己找文件、自己归类、自己成稿，中间遇到拿不准的才回来问你。

注意这个比方的重点不在"更聪明"，而在**他有手**：能打开文件、能执行命令、能上网查、能写东西。能干活的 AI 和不干活的 AI，差别往往不在脑子，在于有没有被允许动手。

### 1.2 和"会聊天的 AI"差在哪

| 维度 | 聊天型 AI | AIAgent |
| --- | --- | --- |
| 谁定步骤 | 你一步步说，它一步步答 | 你给目标，它自己拆步骤 |
| 能不能碰文件 | 不能，除非你粘贴内容进去 | 能读、能改、能新建 |
| 一轮任务多长 | 通常一到几轮 | 可以连续几十步直到收工 |
| 出错怎么办 | 你发现，你重说 | 它自查结果，不对就换法子重试 |
| 交付物 | 一段文字 | 一个改好的文件、一份跑完的报告 |

### 1.3 一次任务里它到底在干什么

它不是一个"输入→输出"的黑箱，而是一个循环。理解了循环，你就知道该在哪一步插手。

```
接目标 ─▶ 看现场 ─▶ 拆步骤 ─▶ 动手 ─▶ 看结果 ─▶ 交付
                              ▲        │
                              └─ 不对 ─┘
                                       │
                                       └─ 卡住了 ─▶ 带着具体问题回来问你
```

| 环节 | 它在做什么 | 你最容易在这里出错的地方 |
| --- | --- | --- |
| 接目标 | 把你的话翻译成一件可执行的任务 | 话说得太虚，它只能靠猜 |
| 看现场 | 读文件、查资料，先弄清现状 | 没告诉它哪些材料是准的，它读了过期的 |
| 拆步骤 | 排先后、选用哪些工具 | — |
| 动手 | 真正执行：改文件、跑命令、发请求 | 没设权限边界，它动了不该动的 |
| 看结果 | 检查每步输出，不对就重试 | — |
| 交付 | 汇总结果，或带着具体问题回来问你 | 没定验收标准，你只能凭感觉看 |

**这个循环解释了 agent 最典型的两种失败**：一种是**在"看现场"就错了**——读了错的资料，后面全错，而且看起来很合理；另一种是**在"看结果"环节自己骗自己**——试了三次没成，就编一个能自圆其说的答案交差。后面第三章的"验收四查"和"停止条件"，就是专门防这两件事的。

### 1.4 它由四块拼成

| 组成 | 作用 | 由谁提供 | 缺了会怎样 |
| --- | --- | --- | --- |
| 大脑 | 大模型，负责理解目标、判断下一步 | 平台 | 完全动不了 |
| 手脚 | 工具：读写文件、执行命令、联网、调接口 | 平台 | 只会空谈，落不了地 |
| 记忆 | 上下文：记住这次任务里已经做过什么 | 平台 | 每一步都要你重新交代 |
| 规矩 | 知道这类活按什么标准干 | **你**（见 [AISkill](../AISkill/README.md)） | 每次做法都不一样 |

前三块装好就能用，第四块决定它干得像不像你的人。这块怎么写，本篇不展开——那是 `AISkill/` 手册的整本书。

### 1.5 自主性分级：谁决定下一步

下面这个分级是个粗略模型，不是行业标准，但足够帮你判断"这件事能放多开"。

| 级别 | 谁决定下一步 | 典型样子 | 适用场景 |
| --- | --- | --- | --- |
| L0 只答不做 | 你 | 聊天、问建议 | 想清楚思路 |
| L1 一步一确认 | 你确认，它执行 | 你点一下，它改一个文件 | 动生产环境、改重要文档 |
| L2 给目标自己做完 | 它，你可随时打断 | 整理一批文件、写一份报告 | 日常大部分活 |
| L3 长任务自调度 | 它，只在节点找你 | 跨多天的调研、批量迁移 | 步骤多但可回滚 |
| L4 自己找活干 | 它 | 自己发现问题、自己发起 | 风险最高，一般不轻易开 |

**新手最常见的错误是直接跳到 L4**：给一句"帮我优化下公司文档"，然后期待奇迹。合理的路径是从 L1 起步，跑顺三次再升到 L2。

### 1.6 几个容易混的词

| 词 | 大白话 | 谁决定做什么 |
| --- | --- | --- |
| 聊天机器人 | 你问它答 | 你 |
| Copilot（副驾） | 它给建议，你来动手 | 你，它只补全 |
| 工作流（Workflow） | 步骤事先画死，按顺序跑 | 流程图，没人临场判断 |
| **Agent（智能体）** | **给目标，它自己决定怎么走** | **它** |
| 技能（Skill） | 它干活时参照的规矩 | 不决定做什么，只决定怎么做 |

最后一行最关键：**技能不产生行动，agent 才产生行动。** 一份写得很好的技能放在硬盘里，不会有任何事发生；把它交给 agent，它才变成行为。

## 二、用途说明：什么活该交给它

### 2.1 三个判断条件

一件事值不值得交给 agent，看三条，缺一条就别急：

| 条件 | 问自己 | 不满足会怎样 |
| --- | --- | --- |
| **说得清** | 我能不能用三句话说清要什么、不要什么 | 它只能猜，产出靠运气 |
| **验得了** | 结果对不对，我能不能在十分钟内看出来 | 你无法判断它交的是好是坏 |
| **退得回** | 做错了能不能撤回、有没有备份 | 一次失误就是永久损失 |

三条都过，放心派；缺"验得了"，先想清楚验收标准再派；缺"退得回"，先做备份，或者只给它只读权限。

### 2.2 适合与不适合

| 适合交给 agent | 为什么 | 例子 |
| --- | --- | --- |
| 步骤多但每步都明确的活 | 它能连着做，不用你盯 | 一批文档转格式 + 抽字段 + 汇总成表 |
| 要跨多个工具搬数据的活 | 人手搬容易错、费时间 | 从网页取数 → 清洗 → 写进表格 |
| 每次情况都不太一样的活 | 需要临场判断，脚本写不死 | 按不同客户资料生成不同方案初稿 |
| 需要先查再答的活 | 它能自己检索、自己核对 | 竞品资料调研与对比 |

| 别交给 agent | 为什么 | 换什么办法 |
| --- | --- | --- |
| 一次性的小事 | 描述成本高于自己做 | 自己两分钟搞定 |
| 规则完全固定、天天一样的活 | agent 有成本、有延迟、还会飘 | 写成脚本或工作流 |
| 结果无法验证的活 | 你分不清它对错，等于赌博 | 先想办法建立验收标准 |
| 不可逆且高风险的活 | 一次失误无法挽回 | 人来执行，agent 只做准备 |
| 需要专业资质判断的活 | 法律、医疗、审计结论不能靠它 | 它做初稿，人签字 |

### 2.3 六类典型场景

| 场景 | agent 干什么 | 你负责什么 |
| --- | --- | --- |
| 文档批量处理 | 批量重命名、转格式、抽字段、合并 | 定规则、抽查 10% |
| 资料检索与综述 | 多来源检索、去重、比对、成稿 | 定问题、判断来源可信度 |
| 数据整理与分析 | 清洗、算指标、出图、写结论 | 定口径、复核结论 |
| 代码修改 | 定位问题、改代码、跑测试 | 定需求、审 diff |
| 例行巡检 | 查日志、比配置、出报告 | 定阈值、处理异常 |
| 跨工具流程 | 搬数据、发通知、更新状态 | 授权、兜底 |

共同点：**agent 干"量大、步骤多、需要判断"的部分，人干"定标准、判可信、签字"的部分。** 一旦你发现自己只是在等它出结果、却完全不知道该怎么验，说明这一步派错了。

### 2.4 它能干，但你别放手

| 红线 | 风险 | 正确做法 |
| --- | --- | --- |
| 删除、覆盖、批量改写 | 不可逆，尤其是没有版本管理的目录 | 先备份，或只给只读；删除走回收站 |
| 对外发送：邮件、发布、付款 | 发出去就收不回 | 让它起草，人来点发送 |
| 权限与密钥 | 一次泄露长期受害 | 不把密钥贴进对话；用最小权限账号 |
| 合规与专业结论 | 出错责任在人不在它 | 它出初稿，人复核并署名 |

这条边界不是不信任技术，是**成本不对称**：让它多干一步省你十秒，出了事你要花十小时收拾。

### 2.5 什么时候用脚本，什么时候用 agent

| | 脚本 | Agent |
| --- | --- | --- |
| 输入 | 每次格式一样 | 每次不一样 |
| 异常 | 提前写死分支 | 临场判断 |
| 成本 | 几乎为零 | 每次都有调用成本与延迟 |
| 可预测性 | 高，跑一万次都一样 | 中，同一句话可能两种走法 |
| 适合 | 每天重复、格式固定的活 | 情况多变、需要判断的活 |

判断方法：**如果这件事你能一遍遍写出完全相同的操作步骤，那就写脚本；如果你每次都要先看一眼情况再决定怎么做，那才用 agent。** 稳定到能写成脚本的活交给 agent，是在为"不确定"付冤枉钱。

## 三、使用指引：怎么把活派出去

### 3.1 起步三条原则

1. **小步**：第一次派活，控制在"十分钟能验完"的规模。别拿整个项目试水。
2. **可验收**：派活的同时想好"什么样算完成"，最好能逐条打勾。
3. **可回滚**：动手前先有备份或版本管理，最差也能 `git checkout` 回来。

### 3.2 派活五段式

大多数人派活失败，不是 AI 不行，是**只说了目标，没说边界和终点**。按这五段写，成功率高得多：

```
目标：把【什么】变成【什么】，交付到【哪里】
输入：这几份是准的（列出路径）；那几份是旧的，不要用
约束：不要改【哪些】；输出用【什么格式】；最多花【多少时间/成本】
验收：满足这【几条】算完成（可逐条打勾）
停止：遇到【什么情况】停下来问我，不要自己决定
```

对照一下差别：

| 说法 | 结果 |
| --- | --- |
| "帮我把会议记录整理一下" | 它按自己的理解整理，格式、详略全靠猜 |
| "把 `meetings/` 下 10 月的 3 份记录合并成一份复盘，输出到 `review/10月复盘.md`；只保留决议和待办，删掉寒暄；每项待办要标负责人；如果某份记录缺少负责人，先在文末列出缺项，不要自己编；改完把文件列表报给我" | 结构、范围、异常处理都定了，产出基本可预期 |

差别不在字数，在于**后一句里有验收标准和停止条件**。

### 3.3 任务怎么拆

拆到"一步一验"就够了，不用拆到原子级。

| 拆得太粗 | 拆得合适 | 拆得太细 |
| --- | --- | --- |
| "整理公司资料" | "把 `docs/` 下的文档按主题分成四类，输出分类表" | "打开第一个文件，读第一段，判断主题……" |
| 它无从下手 | 每步有明确产出，错了能马上发现 | 你在替它写程序，不如自己干 |

一个实用信号：**如果一步做完，你没法在三十秒内判断对不对，就再拆一层。**

### 3.4 权限与安全边界

| 做法 | 具体怎么设 |
| --- | --- |
| 只读优先 | 第一轮只让它读和报，确认理解对了再放开写 |
| 危险操作二次确认 | 明确要求：删除、覆盖、对外发送前必须先问你 |
| 先备份 | 动手前复制一份，或确认目录在版本管理下 |
| 最小权限 | 用专门的、权限受限的账号，别给它主账号密钥 |
| 敏感数据 | 客户名单、身份证号、合同金额不进对话；需要时先脱敏 |
| 小批量 | 批量操作分批做，每批不超过十来个文件，做完抽查 |

### 3.5 过程监督与纠偏

不用全程盯着，但出现这三个信号就该打断：

| 信号 | 说明 |
| --- | --- |
| 开始动你没让它动的东西 | 范围失控，越早停越好 |
| 同一招反复试三次以上 | 它陷在循环里，再试也是白试 |
| 即将执行不可逆操作 | 删除、覆盖、发布、付款 |

打断的正确说法：**"先停，把已经改了哪些文件列给我，不要继续。"** 拿到清单，确认影响范围，再从最近的可回滚点重来。别只说"不对"，那等于让它继续猜。

### 3.6 验收四查

它说"完成了"不算完成，按这四条查：

| 查什么 | 怎么查 | 不过怎么办 |
| --- | --- | --- |
| **查范围** | 对比改动清单，只动了该动的吗 | 有多余改动就回滚，重新限定范围 |
| **查内容** | 逐条对派活时写的验收条件 | 缺哪条补哪条，别整体重做 |
| **查副作用** | 有没有误删、误发、误改别处 | 立刻停，先恢复再谈优化 |
| **查可复现** | 同样的输入再跑一次，结论是否一致 | 差异大说明它靠猜，需要补约束 |

四查里最容易漏的是"查副作用"——结果对了，但顺手改坏了别的东西。所以**要改动清单，不要只看总结**。

### 3.7 跑顺之后：把做法固化下来

同一类活派到第三遍，你大概率在重复说同样的话。这时候该把这段话变成技能文件——**派活的话是给这一次的，技能文件是给每一次的**。

| | 派活的话 | 技能文件 |
| --- | --- | --- |
| 生效范围 | 这一次对话 | 以后每一次 |
| 谁看 | 当前这个 agent | 任何接手的 agent |
| 形态 | 聊天里的一段话 | 仓库里的一个 `.md` |
| 怎么来 | 随口说 | 把跑顺的那段话整理成条款 |

具体怎么写，看 [04 制作步骤](../AISkill/docs/04-制作步骤.md)，模板在 [SKILL-模板](../AISkill/templates/SKILL-模板.md)。本篇不重复讲。

### 3.8 什么时候需要多个 agent

单个 agent 能做完的，别拆。拆成多个只在两种情况下划算：

- **活太长，一个上下文装不下**：比如读完 200 份文档再写综述，拆成"分批读 + 汇总"。
- **需要相互检查**：一个写、一个挑错，比一个自查更可靠。

拆的代价是**信息在交接处丢失**，所以交接时必须给结构化产物（清单、表格、明确结论），不能只说"上面那些你自己看"。

### 3.9 五个典型误区

| 误区 | 表现 | 改法 |
| --- | --- | --- |
| 一句话派大活 | "帮我整理下资料" | 用五段式，先把范围缩到十分钟能验的规模 |
| 把它当搜索引擎 | 直接信它给的数字和出处 | 要求标来源，关键数字自己复核 |
| 不设停止条件 | 它自作主张删了文件、发了邮件 | 明确"遇到 X 先问我" |
| 只看总结不看过程 | 结果对了，别处被改坏 | 每次要改动清单，做"查副作用" |
| 每次都从头交代 | 同一类活派了十遍，每遍都在重复 | 第三遍起固化成技能（见 3.7） |

## 四、一页速查

派活前：

- [ ] 说得清：三句话能讲明白要什么、不要什么
- [ ] 验得了：知道什么样算完成，能逐条打勾
- [ ] 退得回：有备份或版本管理
- [ ] 权限定了：只读还是可写，危险操作要不要二次确认

派活时，五段不能少：**目标、输入、约束、验收、停止**。

派活后，四查不能省：**范围、内容、副作用、可复现**。

三条红线不越：**不逆的操作人来点、对外发送人来发、专业结论人来签**。

同一类活做到第三遍，就别再口头交代了——写成技能，见 [AISkill 手册](../AISkill/README.md)。
