## 7.1 先分清三个层次

| 层次 | 是什么 | 谁负责 | 打个比方 |
| --- | --- | --- | --- |
| **模型能力**：工具调用（Tool Calling） | 模型能输出"我要调某个函数，参数是这些" | 模型厂商 | 厨师会看菜单、会点单 |
| **接入标准**：MCP | 规定工具怎么描述、怎么调用、结果怎么返回 | 协议标准 | 菜单的格式、点单的话术 |
| **产品实现**：Agent 循环 | 决定什么时候调、调几次、要不要确认、错了怎么办 | 你的程序 | 厨房的排班和出菜流程 |

**关键结论**：MCP 只负责中间那层。它让"工具"变得可插拔，但**不负责**"该不该调""调完要不要确认""失败了重试几次"。

---

## 7.2 没有 MCP 时，工具是怎么接的

在 [AgentWorkbench](../../AgentWorkbench/README.md) 这个项目里，AI 能用的六个工具是直接写在代码里的：

```csharp
AIFunctionFactory.Create(tableTools.GetTableSchema)
AIFunctionFactory.Create(tableTools.QueryRows)
AIFunctionFactory.Create(tableTools.ProposeChanges)
// ...
```

这些函数只对"当前打开的这一张表"有效。程序自己定义、自己调用、自己校验。**这在小范围里最简单，也最安全**——因为工具和数据都在同一个程序里，不经过任何外部进程。

---

## 7.3 如果要做成 MCP 服务器，会变成什么

把这六个工具按 MCP 的规范暴露出去，它就成了一个"表格 MCP 服务器"：

```
外部 AI 客户端
   │  按 MCP 标准说话
   ▼
表格 MCP 服务器
   ├─ tools: get_table_schema / query_rows / get_row /
   │         list_column_values / propose_changes / ask_user
   └─ 内部仍然走：校验 → 暂存 → 确认 → 应用 → 审计
```

三件事**不会**因为用了 MCP 而改变：

1. **确认门还在产品这一侧。** 服务器只负责"生成提议"，用户点不点头是客户端和产品的事。MCP 不会替你确认。
2. **校验还在服务器内部。** 十二条校验规则仍然要跑，不能因为"外面是标准协议"就放松。
3. **审计还在服务器内部。** 谁在什么时候调了什么，仍然要记，而且要记到"应用了几条、拒绝了几条"。

> 换句话说：**MCP 换掉的是"接口的形状"，不是"安全的责任"。**

---

## 7.4 一个常见的架构选择

| 做法 | 好处 | 代价 | 什么时候用 |
| --- | --- | --- | --- |
| 工具写在程序里 | 最简单、最快、最安全 | 只能自己用，换客户端要重写 | Demo、单机工具 |
| 包一层 MCP 服务器 | 多个客户端复用、可被别人接 | 多一层进程、多一层权限管理 | 要被多个 AI 共用时 |
| 直接连现成的 MCP 服务器 | 不用自己写 | 权限、数据流向不受控 | 通用能力（搜索、文件、日历） |

判断方法：**这个能力只给我自己这个程序用，还是要给很多 AI 用？** 只给自己，就别上 MCP——多一层就多一处会坏的地方。

---

## 7.5 MCP 和"技能"是互补的，不是竞争的

现在行业里有个共识：**MCP 负责"够得着"，技能（Agent Skills）负责"做得对"。**

- MCP 给你一个 `query_database` 工具，但它不知道你们公司的口径："活跃用户"是指 7 天登录还是 30 天有订单。
- 技能文件里写清楚这个口径、写清楚先查哪张表、写清楚结果要分几段。
- 两者一起用，AI 才既拿得到数据，又算得对。

这正好对应本项目 `AISkill/`（做法）和 `AIMCP/`（接口）的分工。

---

## 本篇要点

- 三层分清：**工具调用是模型能力，MCP 是接入标准，Agent 循环是产品实现**。
- 工具写在程序里最简单；要被多个 AI 共用时，才值得包成 MCP 服务器。
- 包成 MCP 之后，确认门、校验、审计仍然留在产品这一侧。
- MCP 负责"够得着"，技能负责"做得对"，两者互补。
