# AISkill 说明文档

> 版本：v1.0
> 更新日期：2026-10-28
> 适用范围：所有接入 AISkill 规范的 AI 应用、智能体与自动化流程

---

## 一、简介

**AISkill（AI Skill）** 是对 AI 能力的一种标准化封装方式。它把一个可复用的任务能力——包括能力描述、适用场景、输入输出约定、执行步骤以及依赖资源——打包成一个自包含、可被程序化发现的单元，让 AI 应用不必重复编写提示词与流程代码，即可按需调用。

可以把 AISkill 理解为「写给 AI 看的说明书 + 可直接执行的工具」：

- 对**人**而言，它是一份结构化的能力文档，说明了这个技能能做什么、怎么做、有什么限制；
- 对**AI 应用**而言，它是一个可加载的指令包，模型读取后即获得该领域的专业流程、命令用法与判断标准。

AISkill 的核心设计原则是**一次封装、多处复用、按需加载**。技能只在被判定为相关时才载入上下文，避免占用宝贵的上下文窗口，同时保证执行时的专业度与一致性。

### 1.1 一个 AISkill 通常包含什么

| 组成 | 说明 |
| --- | --- |
| 元信息（Metadata） | 名称、版本、描述、触发关键词、适用边界 |
| 指令正文（Instructions） | 该技能的标准作业流程、判断规则、注意事项 |
| 资源文件（Resources） | 模板、脚本、示例、参考文档、数据集等 |
| 依赖声明（Dependencies） | 需要的外部工具、API、环境变量或权限 |

### 1.2 与传统「提示词模板」的区别

| 维度 | 提示词模板 | AISkill |
| --- | --- | --- |
| 组织方式 | 一段文本，散落在代码或文档中 | 目录化封装，元信息与正文分离 |
| 可发现性 | 依赖人工挑选 | 可被应用按描述与关键词自动匹配 |
| 可维护性 | 修改即影响全部调用方 | 版本化管理，支持灰度与回滚 |
| 可执行性 | 通常只描述「怎么做」 | 可携带脚本与工具，直接「替你做」 |
| 边界控制 | 容易越界使用 | 显式声明适用与不适用场景 |

## 二、用途说明

AISkill 主要解决「AI 在特定领域表现不稳定、经验难以沉淀」的问题。典型用途如下。

### 2.1 沉淀专业流程

把团队内部反复验证过的工作流（如发布流程、代码评审规范、报表口径、合同审查清单）固化为技能，让 AI 每次都按同一套标准执行，而不是每次重新「即兴发挥」。

### 2.2 统一输出质量

同一类任务由不同人、不同会话发起时，输出结构、术语、格式保持一致。例如所有周报都遵循同一套章节结构与数据口径。

### 2.3 复用工具与脚本能力

将复杂的命令行调用、API 封装、文件处理逻辑写进技能的资源目录，AI 只需按说明调用，无需现场推导参数，显著降低出错率。

### 2.4 降低上下文成本

技能按需加载：平时只占用一小段描述，命中后才载入完整指令。既节省上下文，又能在需要时获得深度专业支持。

### 2.5 支持团队协作与版本演进

技能以目录 + 文件的形式纳入版本控制，可与代码一同评审、发布、回滚，形成可审计的能力资产库。

### 2.6 不适用场景

- **一次性、临时性任务**：封装成本高于收益，直接对话即可。
- **强实时性、强交互性的操作**：如逐帧操控界面，更适合专用自动化工具。
- **需要模型自主创造性发挥的开放式创作**：过度约束反而限制效果。

## 三、使用指引

### 3.1 目录结构约定

推荐的技能目录结构如下：

```
AISkill/
├── AISkill.md            # 技能说明文档（本文件）
├── SKILL.md              # 技能指令正文（供 AI 加载）
├── references/           # 参考资料：规范、示例、术语表
├── scripts/              # 可执行脚本：转换、校验、批处理
└── assets/               # 模板与静态资源
```

其中 `SKILL.md` 承载元信息与指令，其余目录按需添加。若技能极简，可只保留一份说明文档。

### 3.2 编写一份 AISkill 的步骤

1. **明确能力边界**
   用一句话写清「这个技能解决什么问题」，并列出至少三条「不适用场景」。边界不清是技能失效的首要原因。

2. **编写元信息**
   包括名称、版本、描述与触发关键词。描述要具体，避免「帮助处理文档」这类无法匹配的泛化表述，改为「解析 PDF 并抽取表格，输出为 Markdown 表格」。

3. **拆解执行流程**
   按「判断条件 → 执行动作 → 校验结果」的顺序写成有序步骤。每一步尽量对应一个可验证的动作，避免模糊表述。

4. **附带资源**
   把模板、脚本、示例文件放入对应目录，并在正文中以相对路径引用，保证技能可整体迁移。

5. **声明依赖与限制**
   写明所需工具、权限、网络访问、文件格式限制，避免运行中途失败。

6. **本地试跑与迭代**
   用真实任务验证，记录失败案例并补充到「常见问题」章节。

### 3.3 调用方式

AISkill 的使用遵循「先匹配、后加载、再执行」三步：

1. **匹配**：应用根据用户请求与技能的描述/关键词判断相关性；
2. **加载**：命中后读取 `SKILL.md` 全文，将指令注入上下文；
3. **执行**：按指令中的流程调用工具、处理文件、产出结果。

人工使用时，可直接说明意图或点名技能，例如：

```
使用 AISkill 中的「文档解析」能力，把这个 PDF 的表格导出为 Markdown。
```

### 3.4 编写规范清单

- [ ] 名称唯一，能在一行内说明用途
- [ ] 描述包含「做什么 + 对什么 + 产出什么」
- [ ] 触发关键词覆盖用户的常见说法（含中英文同义词）
- [ ] 执行步骤可被逐步验证，无隐含前置条件
- [ ] 所有引用文件使用相对路径
- [ ] 明确写出不适用场景与已知限制
- [ ] 提供至少一个完整示例（输入 → 处理 → 输出）
- [ ] 版本号与变更记录同步更新

### 3.5 维护与迭代

| 事项 | 建议做法 |
| --- | --- |
| 版本管理 | 采用语义化版本，破坏性变更升主版本号 |
| 变更记录 | 在文末维护 Changelog，记录变更点与原因 |
| 效果评估 | 定期用固定测试任务集回归，对比输出稳定性 |
| 废弃策略 | 标注 `deprecated` 并给出替代技能，保留一个版本周期 |

### 3.6 常见问题

**Q：技能内容写多长合适？**
A：以「能独立完成该类任务」为准。过短缺少关键判断依据，过长会稀释重点。优先把细节移到 `references/` 并在正文中引用。

**Q：多个技能内容重叠怎么办？**
A：合并为一个技能，或明确拆分边界并在描述中互相排除。重叠会导致匹配不确定。

**Q：技能里的脚本可以修改外部文件吗？**
A：应遵循最小权限原则，脚本只操作技能声明的输入输出范围内的文件，涉及删除、覆盖等高风险操作时须要求显式确认。
