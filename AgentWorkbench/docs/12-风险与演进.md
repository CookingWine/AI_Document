## 12.1 风险表

按"会不会让 Demo 当场失败"排序，不按理论严重性排序。

| # | 风险 | 概率 | 影响 | 早期信号 | 对策 |
| --- | --- | --- | --- | --- | --- |
| R1 | 模型 tool calling 不稳，参数老出错 | 高 | 高 | 评测里参数合法率 < 90% | 固定模型版本；工具描述写细；降级到单条 op 工具 |
| R2 | 换模型后行为全变，之前的调优作废 | 高 | 中 | 同一提示词，两个模型输出风格差异大 | 提示词与评测集一起版本化；换模型必须重跑 20 条评测 |
| R3 | 上下文膨胀，慢且贵 | 中高 | 中 | 单轮 tokens > 20k | `query_rows` 夹紧 limit；超预算压缩；日志记 tokens |
| R4 | 主键识别失败，diff 全错 | 中 | 高 | 状态栏主键显示 `__rowid` 且用户不知情 | 导入时明确提示；允许手动指定主键 |
| R5 | 中文列名与格式差异导致类型推断错 | 中 | 中 | 日期列被识别成文本 | 多格式解析；UI 允许改列类型 |
| R6 | DataGrid 表现问题（动态列、性能） | 中 | 中 | 5000 行滚动掉帧、列绑定错位 | 开回收；必要时换只读 `TableView` |
| R7 | 提示词注入（单元格里藏指令） | 低 | 高 | 模型执行了数据里的"指令" | 数据包裹声明 + 确认门（[07](./07-工具与权限门.md) 7.8） |
| R8 | 用户误点接受，改错数据 | 中 | 中 | 演示时点了"全部接受"才发现 | 撤销 + 逐条勾选 + 影响面摘要 |
| R9 | 密钥泄漏（截图、日志、仓库） | 中 | 高 | 日志里出现 `sk-` | 只走环境变量；日志脱敏；提交前 grep |
| R10 | 排期超，砍到核心 | 中 | 中 | M2 拖了两天 | 按 [09](./09-Demo实施计划.md) 9.7 的顺序砍 |
| R11 | 企业环境不允许数据出境 | 中 | 高 | 安全评审问"数据发到哪" | 提供 Ollama 本地模型路径；文档写清发送内容 |
| R12 | macOS 签名/分发被拦 | 低 | 低 | 对方双击没反应 | `xattr` 去隔离；或右键打开 |

三条最该提前埋的：

- **R4（主键）**：M1 就要把"主键是谁"显示在界面上，别等 M2 出错才发现。
- **R2（换模型）**：从第一天起，提示词进版本库、评测集进版本库。没有这两样，换模型等于重做。
- **R11（合规）**：如果观众来自企业，第一天就要能回答"哪些数据会发出去"。答案是：只有列名、类型、行数，以及被查询到的那几行，不含整表。

## 12.2 Demo 到产品，差七件事

Demo 是纵向切了一刀，产品是横向铺开。这七件每一件都不小。

| # | Demo 现状 | 产品需要 | 代价 |
| --- | --- | --- | --- |
| 1 | 单文档 | 工作区、多文档、最近打开 | 中 |
| 2 | 单用户 | 账号、权限、按文档授权 | 大（要服务端） |
| 3 | 内存撤销栈 | 持久化历史、版本树、可回放 | 中 |
| 4 | 工具写死在代码里 | Agent 定义、工具白名单、自主级别 | 大 |
| 5 | 审计写本地文件 | 集中采集、检索、导出、留存策略 | 中 |
| 6 | 一次性评测 | 持续评测、回归门禁、线上采样 | 中 |
| 7 | 无监控 | 延迟、失败率、成本、告警 | 中 |

第 4 项是这个产品真正的"管理"所在。现在的 Demo 里，"Agent"是代码里的一个类；产品里，Agent 应该是一个**可编辑的对象**：

```
Agent 定义
├── 名称、描述、图标
├── 模型（provider + model + 参数）
├── 工具白名单（勾选可用工具）
├── 自主级别（L0 只读 / L1 提议需确认 / L2 低风险自动 / L3 全自动）
├── 挂载的技能（AISkill 格式的 Markdown）
├── 生效的规则（AIRule 格式，转成 rules.json）
└── 预算（每轮 tokens、每任务调用次数、超时）
```

这张表就是 [AIAgents](../../AIAgents/README.md)、[AISkill](../../AISkill/README.md)、[AIRule](../../AIRule/README.md) 三套文档在代码里的合流点。Demo 只实现了 L1 和一套固定规则，但数据结构要按这个形状留接口，否则 M7 会推倒重来。

**建议在 Demo 阶段就做的一件事**：把 `AgentOptions` 从"一个扁平配置类"改成"一个 `AgentDefinition` 对象"，哪怕现在只能从 JSON 读一个。改造成本半天，省下的重构是几天。

## 12.3 演进路线

按价值密度排序，不是按技术难度。

| 阶段 | 主题 | 核心内容 | 判断能不能做的标准 |
| --- | --- | --- | --- |
| M7 | Agent 管理面 | Agent 定义 CRUD、模型切换、工具白名单、自主级别 | 能同时存两个 Agent 并各跑一次 |
| M8 | 技能库 | 导入 AISkill 格式的 Markdown，挂载到 Agent，版本化 | 换技能后同一句话的行为明显不同 |
| M9 | 规则编辑器 | `rules.json` 图形化编辑 + "规则测试器"（喂一条补丁看拦不拦） | 非开发者能自己加一条"月薪上限" |
| M10 | 多文档与批量 | 工作区、跨文档引用、批量任务队列 | 一次对 10 个文档跑同一条指令 |
| M11 | 外部工具 | MCP 接入（数据库、内部 API、文件系统只读） | 接入一个真实数据源且不破坏安全边界 |
| M12 | 协作与治理 | 服务端审计、多人审批、成本看板 | 两个人同时审同一批变更不冲突 |

M7 与 M9 是"管理工具"这个词的正面回答，优先级最高。M10 之后就开始碰服务端，性质变了。

**每一阶段的前置条件只有一条**：上一阶段的审计日志能支撑回放。没有留痕的功能不要上线，出了问题查不出来。

## 12.4 什么时候该动架构

不是"以后可能"，是"看到这个信号就必须改"。列清楚，免得到时候犹豫。

| 信号 | 说明 | 该改成 |
| --- | --- | --- |
| 单文档 > 5 万行 | 全量加载和全表 diff 都撑不住 | 分页加载 + 增量 diff + 列式存储 |
| 需要两人同时编辑同一文档 | 后写覆盖前写会丢数据 | 乐观锁 + 冲突提示；再进一步是 CRDT |
| 需要跨表查询 | 单表模型表达不了 | 关系模型 + 查询层（或直接上数据库） |
| 需要回放任意历史 | 快照栈只有 30 步 | 事件溯源（每次变更存事件而非快照） |
| 工具数 > 15 | 模型选错工具的概率陡增 | 工具分组 + 按场景加载（工具检索） |
| 单轮 > 30 秒 | 用户等不住，界面也不好做 | 后台任务队列 + 完成通知 |
| 单文档 > 50 列 | 表格横向不可用 | 列分组、列显隐、冻结列 |

现在一个都不要做。列在这里是为了**在看到信号时能立刻判断**，而不是被"要不要提前设计"这个问题反复消耗。

## 12.5 三件不要做的事

**一、不要做通用聊天客户端。**
"既然接了模型，不如把模型选择、系统提示词编辑、多会话都做上"——这是另一个产品，而且已经有很多了。这个工具的价值在"表格 + 受控变更"，不在聊天。

**二、不要让模型执行代码或 SQL。**
哪怕只是"帮我算一下平均薪资"，也不要给它 `eval` 或 `run_query`。一旦开了这个口，前面所有校验、确认、审计都可以被绕过。要算就在 Core 里写函数，让模型调用函数。

**三、不要在没跑评测的情况下加工具、换模型。**
每加一个工具，模型的决策空间就大一分；每换一个模型，之前所有的行为假设都要重新验证。凭感觉调，最后会陷入"改 A 坏 B"的循环，而你连基线都没有。

---

## 本篇要点

- 十二条风险里，最该提前埋的是主键识别、评测集、合规口径这三件。
- Demo 到产品差七件事，其中"Agent 变成可编辑对象"是"管理工具"这个词的核心，数据结构现在就要留口。
- 演进按 M7 管理面 → M8 技能库 → M9 规则编辑器推进，M10 之后开始碰服务端。
- 架构变更看信号，不看感觉；七个信号写清楚，看到就改，没看到就别提前设计。
- 三件不做：通用聊天客户端、让模型执行代码、无评测就换模型。
