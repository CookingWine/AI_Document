## 5.1 差异引擎有三个用户

同一个 `Compare` 方法，被三个地方调用，所以它必须又准又快又纯：

| 调用方 | 用来做什么 | 对它的要求 |
| --- | --- | --- |
| 版本对比（M2） | 导入 v2 后告诉你哪里变了 | 准，能处理新增/删除/插入 |
| 变更预览（M4） | 模型提议改 5 格，先看效果 | 与"应用后"完全一致，不能有偏差 |
| 审计与报告（M5） | 导出 Markdown、写日志 | 可序列化，摘要稳定 |

第三条要求最容易被忽略：**预览用的 diff 和真正应用后的 diff 必须是同一个函数算出来的。** 如果预览自己写一套"模拟应用"的逻辑，总有一天两边对不上，而用户只会说"它明明显示改 3 格，结果改了 4 格"。

做法很简单，也是本篇最重要的一条：

```
应用补丁 → 得到新文档 → 对新旧文档跑 Compare
```

不做"边应用边记录"。多算一次全表 diff（5000 行约 100 毫秒），换来预览与结果永远一致，非常划算。

## 5.2 行怎么配对

配对的本质是回答"这两行是不是同一行"。三步，逐级降级，每次降级都记下置信度。

**第一步：按主键值配对（置信度：Key）**

`Row.Id` 就是主键值，两边做字典，O(n)。命中的直接成对。

**第二步：按内容指纹配对（置信度：Fingerprint）**

用于"新文件没有主键列"或"主键列的值被批量改过"的情况。指纹 = 所有非主键列按列顺序拼起来，做类型归一化后取 SHA-256 前 16 位。

只对剩余的、未配对的行做。指纹相同即视为同一行——它有极小的碰撞概率，但在 Demo 规模（5000 行）可忽略，且置信度会标出来。

**第三步：按剩余顺序配对（置信度：Position）**

两边都还有剩，就按出现顺序一对一配。这一步最容易出错，所以**必须在界面上标注"低置信度"**，让用户知道这几行是猜的。

三步走完，仍未配对的：前一边的是"删除"，后一边的是"新增"。

```
before:  E1001 E1002 E1003 E1004
after:   E1001 E1002 E1005 E1003 E1004
                        ↑ 新增，因为 E1003/E1004 靠主键配上了，没被位置挤走
```

这就是有稳定主键和没稳定主键的差别：没有主键时，上面这个例子会报"E1004 删除、E1005 新增、E1003 修改"，三行全错。

**边界：主键重复。** 目标文件里主键重复，直接报 `DUPLICATE_KEY` 并列出重复值，不进入配对。宁可让用户去修数据，也不要猜。

## 5.3 单元格怎么比

按列类型归一化后比较。规则写在一处，`Core/Diff/CellComparer.cs`，别散落。

| 类型 | 归一化 | 相等判定 | 说明 |
| --- | --- | --- | --- |
| `Text` | 去首尾空白 | 序数比较（区分大小写） | 只用于比较，存的原值不动 |
| `Number` | `decimal.TryParse`，InvariantCulture | 数值相等，`1.0 == 1.00` | 解析失败退化为文本序数比较 |
| `Date` | 依次试 `yyyy-MM-dd`、`yyyy/M/d`、`yyyy年M月d日` | 日期相等 | 只比日期，不比时间 |
| `Bool` | `true/false`、`是/否`、`1/0` | 布尔相等 | 解析失败退化为文本比较 |
| 任意 | `null` 与 `""` | **不相等** | 前者是"没填"，后者是"填了空" |

三种情况要特别说明：

1. **数字比较用 `decimal` 不用 `double`。** 薪资、金额用 `double` 会出现 `18000.000000000002`，比较结果飘。
2. **`null` 与 `""` 判为不等。** 这条会让 CSV 往返时偶尔多出一处"修改"，但比"把空值当成空字符串"安全——后者会在导出时把 `null` 写成 `""`，再导入就分不清了。如果确实想放宽，加一个 `DocumentOptions.TreatEmptyAsNull`，默认 `false`。
3. **不要在这里做"业务相等"。** 比如"研发部和研发中心算不算一个部门"——那是数据清洗，不是 diff。diff 只回答"字面值是否改变"。

## 5.4 变更模型

**`src/AgentWorkbench.Core/Diff/ChangeSet.cs`**

```csharp
namespace AgentWorkbench.Core.Diff;

public enum RowChangeKind { Added, Removed, Modified }
public enum MatchConfidence { Key, Fingerprint, Position }

public sealed record CellChange(
    string ColumnId,
    string ColumnName,
    CellValue Before,
    CellValue After);

public sealed record RowChange(
    RowChangeKind Kind,
    string RowId,
    MatchConfidence Confidence,
    IReadOnlyList<CellChange> Cells)
{
    /// <summary>该行的一行摘要，用于列表显示。</summary>
    public string Summary => Kind switch
    {
        RowChangeKind.Added => $"新增 {RowId}",
        RowChangeKind.Removed => $"删除 {RowId}",
        _ => $"{Cells.Count} 处修改"
    };
}

public sealed record ChangeSet(
    string BeforeVersion,
    string AfterVersion,
    IReadOnlyList<RowChange> Rows)
{
    public int AddedCount => Rows.Count(r => r.Kind == RowChangeKind.Added);
    public int RemovedCount => Rows.Count(r => r.Kind == RowChangeKind.Removed);
    public int ModifiedRowCount => Rows.Count(r => r.Kind == RowChangeKind.Modified);
    public int CellChangeCount => Rows.Sum(r => r.Cells.Count);
    public bool IsEmpty => Rows.Count == 0;

    public string Headline =>
        $"{ModifiedRowCount} 行修改（{CellChangeCount} 处） · {AddedCount} 行新增 · {RemovedCount} 行删除";
}
```

`Headline` 直接给界面用，**不要**在 ViewModel 里拼字符串——摘要口径必须唯一，否则界面、报告、日志三处会对不上。

`Confidence` 放在 `RowChange` 上而不是 `ChangeSet` 上：同一次对比里，可能大部分行靠主键配上，少数几行靠位置猜的，得逐行标。

## 5.5 列的变化

Demo 的边界：**列集合必须一致**（按 Id 比较，顺序无所谓），否则直接失败。

```csharp
public sealed record SchemaMismatch(IReadOnlyList<string> Missing, IReadOnlyList<string> Extra);

public CompareResult Compare(TableDocument before, TableDocument after)
{
    var mismatch = CheckColumns(before, after);   // 按 Id 求差集
    if (mismatch is not null)
        return CompareResult.Failed(mismatch);    // 界面提示"列不一致，无法对比"
    // ……
}
```

三个决定及其理由：

- **列顺序变化不算变更。** 用户拖了一下列宽或调整了列序，不该报 50 处修改。按 Id 取列，顺序只影响显示。
- **重命名列 = 删除 + 新增。** 因为 Id 就是表头，改名等于换 Id。Demo 不支持重命名，遇到就报列不一致。产品阶段加"列映射表"解决（用户指定"旧列名 → 新列名"），那时 Id 和 Name 要真正分开。
- **新增列不自动补空。** 缺列就是缺列，让用户决定怎么填。自动补空会让"新增一列"看起来像"全表 5000 行都被修改"。

## 5.6 实现骨架

**`src/AgentWorkbench.Core/Diff/DiffEngine.cs`**

```csharp
public sealed class DiffEngine
{
    public CompareResult Compare(TableDocument before, TableDocument after)
    {
        var mismatch = CheckColumns(before, after);
        if (mismatch is not null) return CompareResult.Failed(mismatch);

        var changes = new List<RowChange>();

        // 1. 按 Id（主键值）配对
        var afterById = after.Rows.ToDictionary(r => r.Id, StringComparer.Ordinal);
        var matchedAfter = new HashSet<string>(StringComparer.Ordinal);

        foreach (var b in before.Rows)
        {
            if (!afterById.TryGetValue(b.Id, out var a)) continue;
            matchedAfter.Add(a.Id);
            AddIfModified(changes, b, a, MatchConfidence.Key, before.Columns);
        }

        // 2. 剩余行按指纹配对
        var leftBefore = before.Rows.Where(r => !afterById.ContainsKey(r.Id)).ToList();
        var leftAfter  = after.Rows.Where(r => !matchedAfter.Contains(r.Id)).ToList();
        var byFingerprint = leftAfter
            .GroupBy(r => Fingerprint(r, before.Columns, before.PrimaryKeyColumnId))
            .ToDictionary(g => g.Key, g => new Queue<Row>(g));

        var stillBefore = new List<Row>();
        foreach (var b in leftBefore)
        {
            var fp = Fingerprint(b, before.Columns, before.PrimaryKeyColumnId);
            if (byFingerprint.TryGetValue(fp, out var q) && q.Count > 0)
            {
                var a = q.Dequeue();
                matchedAfter.Add(a.Id);
                AddIfModified(changes, b, a, MatchConfidence.Fingerprint, before.Columns);
            }
            else stillBefore.Add(b);
        }

        // 3. 剩下的按位置配对
        var stillAfter = leftAfter.Where(r => !matchedAfter.Contains(r.Id)).ToList();
        for (var i = 0; i < Math.Min(stillBefore.Count, stillAfter.Count); i++)
        {
            matchedAfter.Add(stillAfter[i].Id);
            AddIfModified(changes, stillBefore[i], stillAfter[i], MatchConfidence.Position, before.Columns);
        }

        // 4. 收尾：真正的增删
        foreach (var b in stillBefore.Skip(stillAfter.Count))
            changes.Add(new RowChange(RowChangeKind.Removed, b.Id, MatchConfidence.Key, []));

        foreach (var a in stillAfter.Skip(stillBefore.Count))
            changes.Add(new RowChange(RowChangeKind.Added, a.Id, MatchConfidence.Key, []));

        return CompareResult.Ok(new ChangeSet(
            before.Version.ToString(), after.Version.ToString(), changes));
    }

    private static void AddIfModified(
        List<RowChange> sink, Row b, Row a, MatchConfidence confidence,
        IReadOnlyList<ColumnDef> columns)
    {
        var cells = new List<CellChange>();
        foreach (var col in columns)
        {
            if (!CellComparer.Equal(col, b[col.Id], a[col.Id]))
                cells.Add(new CellChange(col.Id, col.Name, b[col.Id], a[col.Id]));
        }
        if (cells.Count > 0)
            sink.Add(new RowChange(RowChangeKind.Modified, a.Id, confidence, cells));
    }
}
```

上面第 4 步的两行 `Skip` 有个隐含前提：位置配对之后剩下的，一定是"多出来的那部分"。当两边剩余数量不等时，短的先配完，长的后缀就是增或删。这个前提成立，但在实现时要加断言，否则数组越界会以最难看的方式暴露。

`Fingerprint` 只取非主键列，且按列顺序拼接：

```csharp
private static string Fingerprint(Row row, IReadOnlyList<ColumnDef> columns, string primaryKeyColumnId)
{
    var sb = new StringBuilder();
    foreach (var col in columns)
    {
        if (col.Id == primaryKeyColumnId) continue;      // 主键不参与指纹
        sb.Append(col.Id).Append('=')
          .Append(CellComparer.Normalize(col, row[col.Id]))
          .Append('\u001F');                            // 用不可见分隔符，避免 "ab|c" 与 "a|bc" 撞车
    }
    return Convert.ToHexString(SHA256.HashData(Encoding.UTF8.GetBytes(sb.ToString())))[..16];
}
```

`primaryKeyColumnId` 必须显式传进来，不要用"第一列"这种约定——第一列不是主键的情况比想象中常见。

## 5.7 高置信度与低置信度怎么呈现

界面上不能只给一个数字，要给"这次对比有多可信"：

| 置信度 | 界面表现 | 用户该做什么 |
| --- | --- | --- |
| Key | 正常显示，绿色对勾 | 直接看 |
| Fingerprint | 行尾标 `≈`，悬浮提示"按内容匹配" | 抽查两行 |
| Position | 行尾标 `?`，黄色底 | 逐行确认，尤其注意插入/删除附近 |

如果一次对比里 `Position` 占比超过 20%，界面上给一条横幅：**"本次对比主键匹配率偏低，建议指定主键列后重新对比。"** 这比让用户自己发现"怎么全红了"友好得多。

## 5.8 导出报告

同一份 `ChangeSet` 渲染成 Markdown，给验收和存档用。格式固定，不要每次不一样：

```markdown
# 变更报告：员工花名册

基线 v3 → 目标 v4 · 生成于 2026-11-05 10:12 · 主键：工号

## 摘要

- 修改 6 行，共 6 处单元格
- 新增 2 行
- 删除 1 行

## 明细

### 修改（节选）

| 行 | 列 | 原值 | 新值 |
| --- | --- | --- | --- |
| E1003 | 月薪 | 18000 | 18900 |
| E1007 | 部门 | 研发 | 平台研发 |

### 新增

| 行 | 姓名 | 部门 | 月薪 |
| --- | --- | --- | --- |
| E1042 | 周敏 | 设计 | 19000 |

### 删除

| 行 | 姓名 | 部门 |
| --- | --- | --- |
| E1019 | 李强 | 市场 |
```

Markdown 而不是 HTML/PDF：能进 Git、能在 PR 里 review、能被下一个 AI 读懂。导出代码放在 `Infrastructure/Reporting/MarkdownReportWriter.cs`，输入只有 `ChangeSet` 和两个文档，不碰界面。

## 5.9 必测用例

差异引擎是整个 Demo 最该被测试覆盖的地方，没有之一。十条用例，写在一个文件里：

| # | 场景 | 期望 |
| --- | --- | --- |
| 1 | 两份完全相同的文档 | `IsEmpty == true` |
| 2 | 改一个单元格 | 1 行修改，1 处变更 |
| 3 | 中间插入一行 | 1 行新增，其余 0 变更（不级联） |
| 4 | 删除中间一行 | 1 行删除，其余 0 变更 |
| 5 | 首尾各插入一行 | 2 行新增 |
| 6 | 列顺序调换 | 0 变更 |
| 7 | `1.0` vs `1.00` | 0 变更 |
| 8 | `2026-01-01` vs `2026/1/1` | 0 变更 |
| 9 | `null` vs `""` | 1 处变更 |
| 10 | 目标文件主键重复 | 返回 `DUPLICATE_KEY`，不抛异常 |

第 3 条是这套算法的价值所在，也是"用行号配对"的实现唯一过不去的一条。写完先跑它。

## 本篇要点

- 三个用户（对比、预览、报告）共用一个 `Compare`，**预览不做模拟应用**。
- 行配对三步降级：主键 → 指纹 → 位置，后两级必须标低置信度。
- 比较规则集中在 `CellComparer`：文本去空白、数字用 decimal、日期只比日期、`null ≠ ""`。
- 列集合必须一致，列顺序不算变更；重命名等于删加，Demo 不支持。
- 十条用例里，第 3 条（中间插入不级联）是验收这套算法的关键。
