## 2.1 一句话架构

**界面只负责显示和收集意图，Core 负责算得对，Agents 负责跟模型打交道，Infrastructure 负责读写磁盘。**

四句话对应四个项目，加一个只做组装的 App。任何功能先问"它属于哪一句"，归属清楚再写代码。

---

## 2.2 分层与依赖方向

```
AgentWorkbench.App            Avalonia 界面、ViewModel、DI 组装
   │
   ├──▶ AgentWorkbench.Agents         Agent 循环、工具、提示词
   │        │
   ├──▶ AgentWorkbench.Infrastructure 文件读写、配置、审计日志
   │        │
   └────────┴──▶ AgentWorkbench.Core  领域模型、差异引擎、补丁校验（零外部依赖）
```

三条硬规矩：

1. **箭头只能向下。** Core 不认识 Avalonia，也不认识 `IChatClient`；它只认识 `TableDocument` 和 `TablePatch`。这条守住了，差异引擎就能脱离界面单独测、单独跑批。
2. **Agents 不直接改文档。** 它只能产出 `TablePatch`，能不能落地由 App 层的确认门决定。这是整个产品的安全边界，落地方式见 [07](./07-工具与权限门.md)。
3. **Infrastructure 不反向调 Agents。** 需要通知界面时用事件或返回值，不要在里面 `new Window()`。

| 项目 | 管什么 | 不管什么 | 依赖 |
| --- | --- | --- | --- |
| `AgentWorkbench.Core` | 文档模型、类型校验、差异计算、补丁应用、规则校验 | 界面、网络、文件格式 | 无（仅 BCL） |
| `AgentWorkbench.Agents` | `IChatClient` 封装、系统提示词、Agent 循环、工具定义 | 直接写文件、直接改文档 | Core、Microsoft.Extensions.AI |
| `AgentWorkbench.Infrastructure` | CSV/JSON 读写、配置加载、审计日志、密钥读取 | 业务判断 | Core |
| `AgentWorkbench.App` | 窗口、ViewModel、命令、状态机、确认门 | 差异算法、提示词细节 | 以上全部 |
| `tests/*` | 单测与集成测试 | — | 对应项目 |

## 2.3 五个关键决策

每条都写清"选了什么、为什么不选另一个、什么时候该推翻"。这些是后面所有代码的前提，改动代价最大。

### 决策一：Avalonia，不是 WPF 也不是 WinUI

**理由**：你现在的开发机是 macOS（arm64），WPF 和 WinUI 都只能在 Windows 上跑，写完没法在本机看效果。Avalonia 一套 XAML 三平台一致，Skia 自绘，不依赖系统控件，macOS 上的观感和 Windows 基本一样。

**代价**：生态比 WPF 小，第三方控件少；DataGrid 处于维护模式；某些 XAML 写法与 WPF 有差异（`Binding` 的 `ElementName`、样式选择器优先级）。

**什么时候推翻**：只交付 Windows 且必须用系统原生控件或已有的 WPF 资产。那时用 Avalonia XPF 迁，比重写便宜。

### 决策二：JSON 是唯一真源，CSV/XLSX 只是进出口

**理由**：CSV 存不住行标识、列类型、版本号；XLSX 存得住但二进制、diff 不可读、样式噪音大。Demo 需要一个**能进 Git、能人眼读、能稳定承载 RowId** 的格式，JSON 是唯一合适的。

**代价**：用户每次都要"导入 CSV → 另存为 JSON"，多一步。可以用"打开 CSV 时自动在同目录生成同名 `.table.json`"来掩盖。

**什么时候推翻**：接入数据库或多人协作。那时真源换成服务端，JSON 退化为导出格式。

### 决策三：自己写 Agent 循环，不用自动函数调用

**理由**：`Microsoft.Extensions.AI` 提供 `UseFunctionInvocation()`，能自动把模型的工具调用执行掉、把结果回灌、继续下一轮。很方便，但**它会在模型决定的那一刻就执行**——没有地方插"等一下，让我看看要改什么"。

本产品的核心体验恰恰是那个"等一下"。所以：用 `AIFunctionFactory` 生成工具 schema，但**执行权在自己手里**，变更类工具只暂存不落地。

**代价**：要自己写循环、自己处理多轮工具调用、自己做超轮次保护。约 200 行代码，第 06 篇给完整实现。

**什么时候推翻**：做纯只读助手（比如报表问答），没有副作用，自动调用更省事。

### 决策四：变更以 Patch 为单位，不以"对话即改"

**理由**：模型一次说"把研发部所有人薪资上调 5%"，可能涉及 12 行。如果边聊边改，用户看到的是表格在眼前跳动，既不知道改了几处，也没法只拒绝其中一条。用 Patch 表达，就有三样东西同时成立：**预览**（先算差异再显示）、**审阅**（逐条勾选）、**撤销**（保存应用前快照）。

**代价**：多一层 `TablePatch` 模型和校验器，约 300 行。

**什么时候推翻**：不需要，这是长期正确的设计。产品化后 Patch 还能变成协作和审计的基本单位。

### 决策五：稳定 RowId + 显式主键

**理由**：差异计算的准确率完全取决于"这两行是不是同一行"。用行号配对的算法，在中间插入一行之后会把后面所有行都判成"修改"。所以每行必须有稳定标识：导入时若有主键列（如工号）就用它，没有就生成 `r-0001` 这类不可变 Id 并写进 JSON。

**代价**：CSV 本身没有 Id，第一次导入要生成并让用户接受这个副作用；跨文件对比时必须靠主键列对齐。

**什么时候推翻**：不需要。任何做表格 diff 的产品最终都会走到这一步。

## 2.4 两条数据流

程序里只有两条主干，其余都是支线。

**第一条：文件进，表格出**

```
CSV/XLSX ──读──▶ 解析为行与列 ──校验类型──▶ TableDocument（不可变）
                                                  │
                                       绑定──▶ 表格 ViewModel ──▶ DataGrid
```

**第二条：一句话进，变更出**

```
用户输入 ──▶ Agent 循环 ──▶ 只读工具（直接执行，结果回灌）
                    │
                    └──▶ 变更提议（校验 + 暂存，不落地）
                                  │
                            差异预览 ──▶ 用户确认 ──▶ 应用到新版本
                                  │                        │
                              拒绝并说明 ──▶ 回灌给模型    └──▶ 审计日志 + 撤销栈
```

注意第二条里**没有任何一条线从模型直接指向文档**。所有写操作都要经过"校验 → 暂存 → 用户确认 → 生成新版本"四道手续，这是 07 篇的全部内容。

## 2.5 明确不引入的东西

Demo 阶段引入这些，等于给自己挖坑：

| 不引入 | 原因 | 替代做法 |
| --- | --- | --- |
| 数据库（SQLite/Postgres） | 单文档场景，文件足够；引了就要处理迁移、连接、事务 | 一个 JSON 文件 + 内存快照 |
| 消息队列 / 事件总线 | 单进程单用户，没有异步解耦需求 | `event` + `INotifyPropertyChanged` |
| 插件框架 / MEF | 只有一个 Agent，抽象没有第二个样本 | 接口 + DI 注册，等第二个再抽 |
| 自研 ORM / 代码生成 | 领域模型只有四个类型 | 手写 |
| 日志框架全家桶（Serilog + Seq + ...） | 只需要落文件看 | `Microsoft.Extensions.Logging` + 一个文件 Provider |
| 状态管理库（ReactiveUI 全套） | CommunityToolkit.Mvvm 够用，学习成本低 | `ObservableObject` + `RelayCommand` |

一句话原则：**Demo 阶段每引入一个依赖，都要能说出它替你省下的那两天在哪。**

## 2.6 判断"这段代码该写在哪"

三个问句，从上往下问，先命中先归属：

1. **它需要联网或认识模型吗？** 是 → `Agents`。
2. **它需要碰文件、配置、系统路径吗？** 是 → `Infrastructure`。
3. **它只处理数据、不碰外界吗？** 是 → `Core`。
4. 都不是 → `App`，并且大概率是 ViewModel。

举例：

| 需求 | 归属 | 理由 |
| --- | --- | --- |
| 判断某单元格值是否符合列类型 | Core | 纯数据判断 |
| 把两个文档的差异渲染成红色 | App | 显示逻辑，颜色不属于领域 |
| 读取 `appsettings.json` 里的模型名 | Infrastructure | 碰配置 |
| 决定下一步调用哪个工具 | Agents | 认识模型 |
| 阻止用户修改"工号"列 | Core（判定）+ App（提示） | 规则在 Core，提示文案在 App |
| 把审计日志写成 JSONL | Infrastructure | 碰文件 |

## 本篇要点

- 五个项目，箭头只向下，Core 零外部依赖——这条守住了，测试和重构都轻松。
- 五个关键决策里，最重要的是**决策三**（自己写循环）和**决策四**（Patch 为单位），它们共同定义了产品体验。
- 两条数据流，第二条里模型**永远不直接写文档**。
- 不引入数据库、队列、插件框架、重型日志——Demo 阶段每一个依赖都要能说清省了哪两天。
